## 1. 選定の前提（基本設計からの継承）

- 構成は「エージェントが指揮、スクリプトが実行、人間は入口（Slack依頼）と出口（公開確認）だけ」。

## 2. エージェント基盤の選定

### 2.1 評価基準（基本設計の5基準）

1. ブラウザ操作の可否
2. 月2,000円以内に収まる実行コスト（月4回＋例外対応）
3. 共用アカウントで運用できるか
4. 日本語の読解・判断精度
5. Slack / Zoom / YouTube連携のしやすさ

### 2.2 選定の前提を変える調査結果：CanvaはAPIで取れる

基本設計では「Canva素材の取得にブラウザ操作が効く。最大の差別化点」としていたが、調査の結果、**Canva Connect APIにデザインのエクスポート用エンドポイントがあり、MP4（1080p含む）の書き出しが公式に可能**であることが判明した。

- `POST https://api.canva.com/rest/v1/exports`（`design_id`＋`format: mp4`、`quality: 1080p`を指定）。非同期ジョブで、完了後にダウンロードURL（24時間有効）を取得する。スコープは `design:content:read`。
- 出典：Canva Developers 公式リファレンス「Create design export job」。

このため、OP/ED素材の取得は **APIを第一経路**にでき、ブラウザ操作は「Canva APIが使えない場合のフォールバック」に格下げできる。したがって基準1（ブラウザ操作）は選定の必須条件ではなくなり、**エージェント基盤は「判断の質・コスト・共用運用のしやすさ」で選ぶ**のが正しい。ブラウザ操作が要るのは、connpassページの取得などAPIのない相手への予備手段に限られる。

ただし注意点が2つある。

- Canva Connect APIを使うには、Canva側でアプリ（インテグレーション）を作成し、素材の持ち主（作り手）のアカウントでOAuth認可を受ける必要がある。作り手が誰かは未確認（基本設計の未確定事項）。作り手の協力が得られない場合はブラウザ操作にフォールバックする。
- デザインIDの特定（「今回の素材はどれか」）はAPIの一覧・検索（`GET /v1/designs`）で絞り込むが、最終的な対応づけはエージェントの判断になる。

### 2.5 各候補の補足とリスク

- **A. Claude API＋Agent SDK（推奨）**：Agent SDKはClaude Codeのエージェントループ・ツール・権限・MCPをPython/TypeScriptライブラリ化したもので、APIキーで課金される（サブスクリプションとは別）。`max_budget_usd`で1回の予算上限を指定でき、暴走時の支出を抑えられる。モデルは明示的に指定する（既定はOpus 5.5なので、Sonnet 5.5 / Haiku 5.5を指定しないと高くつく）。Consoleでワークスペースを分け、共用アカウント用のAPIキーに月額の支出上限を設定できる。日本語の読解・判断は本件の用途（依頼文・VTT・connpassの読み取り、例外の振り分け）に対して十分。
  - 個人のClaude Codeサブスクリプションに載せる案は不採用。共用アカウント運用（基本設計の決定）と合わず、サブスクリプションの利用枠は個人紐づけでチーム運用に不向きなため。APIキー方式にする。
  - リスク：AnthropicのAPIは仕様変更が速い（2026-10-21のAPIバージョン更新でSDKのメジャーバージョンアップと破壊的変更があった）。バージョンを固定し、変更時は手順書と一緒に更新する。
- **B. OpenAI API**：GPT-5 / GPT-5 mini / GPT-5 nanoは**2026-12-11に廃止予定**で、後継はGPT-6.1-sol / terra / lunaと案内されている（OpenAIの廃止予定表。2026-11-15時点の確認）。選定直後にモデル移行が必須になるため、現時点での新規採用は見送る。後継モデルの料金はGPT-5 mini比で約4倍（入力$0.25→$1）だが、それでも月100円未満で枠内ではある。
- **C. Gemini API**：Gemini 3 Flashは$0.50/$3と安く、日本語も強い。次点として有力。ただしエージェント基盤としてのツール・MCPエコシステムはClaudeほど成熟しておらず、またモデル名・料金の変動が激しい（3系・3.5・3.6・3.7と短期間で世代が進んでいる）。Claudeで躓いた場合の切替先として確保しておく。
- **D. Dify**：Cloud版はProfessional $59/月（年払い$590）で月2,000円の枠を大きく超える。セルフホスト版は無料だが、Dockerで複数サービスを動かす構成で、2GBクラスのVPSでは余裕が少ない。本件は「判断中心のエージェント＋重いffmpeg処理」で、Difyの強み（RAG・チャットアプリ）とは噛み合わない。
- **E. n8n**：Cloud版はStarter €20/月（約3,500円）で枠外。セルフホスト版は無料・軽量（2GBで動作）で、Slackトリガー・Zoom/YouTubeノード・リトライ・実行履歴の可視化が付く。本件の「Slackをトリガーにスクリプトを回す」部分だけをn8nに任せ、判断だけLLMノードに逃がす構成も可能。ただし判断ロジックがワークフロー内に散らばり、保守性はPythonデーモンより落ちる。**第一案では採用せず、PoCで「トリガー・キュー・再試行の器」として併用するかを判断する。**
- **F. 自作ループ**：Messages API等を直接叩き、ツール呼び出しループを自作する案。最も軽量で、Agent SDKのバンドルバイナリ（約346MB）も不要。ただしリトライ・権限制御・MCP接続を全部自作することになる。Agent SDKで躓いた場合の簡素化先として確保しておく。ツール呼び出し層を分離して設計しておけば、A→Fへの置き換えは容易。

### 3.2 選定の考え方

- **CPUコア数が処理時間の鍵**。libx264のエンコードはマルチスレッドでほぼリニアに速くなる（ただし4コア超では頭打ち気味）。2コアでは15分以内は厳しい見込みで、4コアが欲しい（§5の実測参照）。
- **月2,000円の枠内で4コアが取れるのは、実質KAGOYA 4GB（1,760円）だけ**（月払い・前払いなしで）。ConoHa・ABLENETの4GBは長期前払いなら枠内に入るが、初回は1年分前払い（ConoHa 4GB 12ヶ月で21,492円）が必要で、PoC段階での採用には重い。
- **ストレージは100GBあれば十分**。97分の1080p Zoom録画は1〜2GB程度と見込まれ、元動画＋中間ファイル＋出力で1本あたり4GB程度。月4本を回しても、処理後に元動画を削除する運用なら100GBで足りる。KAGOYA 4GBのNVMe 600GBは余裕が大きい。
- **受付状況の注意**：2026年10〜11月はLinuxカーネル脆弱性対応や在庫逼迫で、複数社が新規受付を一時停止した。ConoHaは11/13に再開したとの報道の直後に再停止の報道もあり、状況が流動的である。申込時に各社の公式お知らせで受付状況を必ず確認すること。KAGOYAは2026-11-17時点で受付中とされている。
- **国内決済の観点**：KAGOYA・さくら・ConoHa・ABLENET・XServerはいずれも国内事業者で、日本円・国内カード決済が可能。ユーザーの海外決済の失敗経験を踏まえ、実行環境はこの中から選ぶ。LLM API（Anthropic等）の課金は米ドル建ての海外決済になるが、月100〜200円の従量制で、支出上限を設定できるため、失敗時の影響は小さい。

### 3.3 実行環境の推奨

**第一候補：KAGOYA CLOUD VPS 4GB（1,760円/月）**。理由は、月払い・前払いなしで4コアが取れる唯一の候補で、NVMe 600GBと容量にも余裕があるため。日額課金（63円/日・月額上限1,760円）のため、PoCで数日だけ使ってやめる場合の無駄も小さい。

**第二候補：ConoHa VPS 2GB（まとめトク12ヶ月・980円/月）**。3コアで処理時間が足りることが実測で確認できれば、こちらでもよい。ただし12ヶ月分（11,760円）の前払いが必要で、PoC段階での採用には向かない。月払い（1,259円）でも枠内だが、4GBへの乗り換えは月額が枠を超える。

**第三候補：さくらのVPS 2GB（1,738円/月）**。3コア。2週間の無料お試し（クレジットカード払い）があり、PoCの実測用には最も手軽。ただし4GBが3,520円と枠を大きく超えるため、3コアで処理時間が足りないと判明した場合の逃げ道がない。

**PoCでの進め方**：まずKAGOYA 4GB（または無料お試しのあるさくら 2GB）で実機ベンチマークを取り、§5の見込みを実測で置き換える。KAGOYAは日額課金なので、PoCで数日使って合わなければ解約する、という進め方ができる。

## 4. 推奨構成（1つに絞った具体案）

```
Slack（依頼チャンネル）
  │ Socket Mode（受信・返信。公開URL不要）
  ▼
KAGOYA CLOUD VPS 4GB（1,760円/月）上の常駐デーモン
  ├─ Slack Bolt（Python）：依頼の受信・確認・完了/失敗通知
  ├─ Claude Agent SDK（Sonnet 5.5 主 / Haiku 5.5 従）：指揮役
  │    ├─ 対象の特定（依頼文→録画・connpass・Canva素材の対応づけ）
  │    ├─ 開始点判定の補助（確信度が低い場合のみ）
  │    ├─ 概要欄の生成（connpass転記＋定型部品）
  │    └─ 例外の振り分け（怪しい回は止めてSlackで人間に確認）
  ├─ スクリプト群（実行役。現行ツールを流用）
  │    ├─ Zoom API（Server-to-Server OAuth）：録画・VTT取得
  │    ├─ Canva Connect API：OP/ED素材のエクスポート（MP4 1080p）
  │    ├─ edit.py（1パス化・preset見直し後）：編集・エクスポート
  │    ├─ YouTube Data API v3：非公開アップロード＋メタデータ設定
  │    └─ connpassページ取得：概要欄のもと情報
  └─ 台帳（回・日時・登壇者・公開URLの一覧。SQLiteまたはCSV＋Git管理）
  ▼
YouTube（非公開アップロード）→ 人間が最終確認して公開
```

### 4.1 月額試算（推奨構成）

| 項目 | 月額 |
|---|---|
| KAGOYA CLOUD VPS 4GB | 1,760円 |
| Claude API（Sonnet＋Haiku使い分け、月6回起動） | 約70〜130円 |
| Slack（カスタムアプリ・Socket Mode） | 0円 |
| Zoom API・YouTube API・Canva Connect API | 0円（API利用料なし） |
| **合計** | **約1,830〜1,890円** |

月2,000円の枠内に収まる。ただし為替（1ドル＝150円換算）とLLMの利用量の見積もりに依存する。余裕は約110〜170円しかないため、**支出上限の設定と月次の利用量チェックを運用ルールに入れる**（Claude Consoleのワークスペース支出上限を月500円に設定する等）。

余裕を大きくしたい場合の選択肢：

- VPSをConoHa 2GB（まとめトク12ヶ月・980円/月）にすると合計約1,050〜1,110円になるが、3コアで処理時間が足りるかの実測が前提で、12ヶ月前払いが必要。
- LLMをHaiku 5.5中心にすると月6円程度まで下がるが、判断の質はSonnetより落ちる。定型部分（概要欄の整形・通知文）をHaiku、判断部分（対象特定・例外振り分け）をSonnetに分ける使い分けが現実的。

### 4.2 処理時間の見込み

詳細は§5参照。結論のみここに書く。

- **現行2パス構成のままでは、15分以内は満たせない。** このVMでのedit.py実測（Zoom風素材）では、2パス・fastで97分換算約108分、2パス・veryfastで約79分かかった。4コアVPSへの外挿（約2.7倍速と仮定）でも、2パス・veryfastで約29分と試算され、15分以内には届かない。
- **満たすための条件は3点セット：(a) 4コアのVPS、(b) 1パス化（§6.1）、(c) プリセット veryfast（§6.2）。** これにより処理時間は現行の約1/4〜1/5になる見込みだが、最終的な合否はPoCでの実機・実素材の実測で判定する。
- **Zoom風素材（静止スライド＋小さな話者映像）での実測は§5.3参照。** 実際のZoom録画は重い素材より大幅に速くエンコードできる見込みで、実素材での実測値が最終判断の鍵になる。
- ダウンロード・アップロードの時間は別枠。97分のZoom録画（1〜2GB程度）のダウンロードと、完成動画のYouTubeへのアップロードは、VPSの回線速度（通常1Gbps共有）に依存し、数分程度と見込まれる。編集・エクスポートの15分以内とは別に、全体のリードタイムとして数分を見込んでおくこと。

### 4.3 セットアップ手順の概要

1. **共用アカウントの用意**（ユーザー）：運用専用の共用アカウントを1つ作る。VPS・Claude API・Zoom・YouTube・Canva・Slackの各サービスの認証情報をこのアカウントに紐づける（基本設計の決定事項）。
2. **VPSの契約・初期設定**（ユーザー＋実装者）：KAGOYA 4GBを契約。Ubuntu 24.04、ffmpeg・Python・Node.js（Agent SDK用）を導入。SSH鍵認証・ファイアウォール（22番のみ許可＋SlackはSocket Modeのため受信ポート不要）を設定。

5. **Zoom Server-to-Server OAuthアプリの作成**（ユーザー：Zoomアカウントの管理者は石川さん本人と確認済み）：Zoom MarketplaceでS2S OAuthアプリを作成し、録画の読み取りスコープ（`recording:read`等）を付与。クライアントID・シークレット・Account IDをVPSに設定。
6. **YouTube APIの有効化・OAuth設定**（ユーザー）：Google Cloudでプロジェクトを作成し、YouTube Data API v3を有効化。OAuth同意画面を「本番」状態にし（リフレッシュトークンの7日失効を避けるため）、チャンネルの管理者ロールを持つアカウントで認可を受ける。アップロードは非公開で行う。
7. **Canva Connect APIアプリの作成**（ユーザー＋素材の作り手）：Canva Developersでインテグレーションを作成し、`design:content:read`スコープでOAuth認可を受ける。素材の作り手のアカウントでの認可が必要な場合は、作り手に協力を依頼する。認可が得られない場合はブラウザ操作（Playwright MCP経由）にフォールバックする。
8. **デーモン・スクリプトの配置**（実装者）：リポジトリをVPSに配置。Slack Boltのデーモン、Agent SDKの指揮スクリプト、edit.py（1パス化後）、Zoom/YouTube/Canvaの接続スクリプトを配置し、systemdで常駐化する。ジョブ台帳・ログの置き場を決める。
9. **PoC（1本通し）**：過去の1回分（または次回の1回分）で、Slack依頼→録画取得→編集→非公開アップロード→通知までを1本通す。処理時間を実測し、開始点・無音カット・概要欄の品質を現行の公開動画と見比べる。
10. **定常化**：PoCで問題がなければ、次回以降の本番運用に切り替える。手順書（運用・トラブル対応・引継ぎ）をリポジトリに残す。

## 5. ffmpegエンコード速度の実測と処理時間の判定

### 5.1 実測条件

- 実測環境：このVM（AMD EPYC 9D64、論理CPU 4、**共有CPUクォータ 1.5CPU**、メモリ 7.7GB）。ffmpeg 8.1.2、libx264、crf 18。
- 素材A（重い・保守的）：`testsrc2` で生成した 1920x1080・30fps・180秒の動画。画面全体が動き続ける合成パターンで、実際のZoom録画（スライド中心・動きが少ない）よりエンコードが重い。**この素材での数値は「ワーストケースに近い見積もり」として読むこと。**
- 素材B（Zoom風・現実的）：静止スライド背景＋右下の小さな話者映像（PiP）＋音声（20秒発話＋10秒無音の繰り返し）の180秒動画。実際のセミナー録画に近い構成。
- 音声：いずれもAAC 192k。無音検出は `silencedetect=noise=-38dB:d=3`（現行設定と同じ）。
- 97分動画への換算：97分＝5,820秒。測定した180秒素材の壁時間を32.33倍（5,820÷180）して換算する。無音カットで除去される分（数%程度）は換算に含めていない（＝やや長めの見積もり）。
- 15分以内＝900秒、目標9分＝540秒。**2パス構成では1パスあたり450秒（15分の場合）・270秒（9分の場合）以内、1パス構成では900秒・540秒以内**に収める必要がある。倍速で言うと、2パス構成では1パスあたり12.9倍速（15分）・21.6倍速（9分）、1パス構成では6.5倍速・10.8倍速が必要。

### 5.2 実測結果（素材A：testsrc2、重い素材）

| テスト | 壁時間（180秒素材） | 速度 | 97分動画への換算（1パス分） |
|---|---|---|---|
| 生エンコード fast、threads=1 | 322秒 | 0.559倍速（17fps） | 174分 |
| 生エンコード fast、threads=2 | 336秒 | 0.538倍速（16fps） | 180分 |
| 生エンコード fast、threads=既定（4） | 337秒 | 0.534倍速（16fps） | 182分 |
| 生エンコード medium、threads=既定（4） | 360秒 | 0.50倍速（15fps） | 194分 |
| 生エンコード veryfast、threads=既定（4） | 136秒 | 1.33倍速（40fps） | 73分 |
| 無音検出のみ（音声デコード） | 約1秒 | 751倍速 | 約30秒 |
| edit.py フルパイプライン（2パス、preset fast） | 403秒 | 2パス合計で0.45倍速相当 | 217分 |

実測スクリプトと生ログは `bench/`（`run_bench_v2.sh`、`run_rest.sh`、`bench_results.txt`、`bench_results_v1_raw.txt`）に残してある。

### 5.3 実測結果（素材B：Zoom風、現実的な素材）

| テスト | 壁時間（180秒素材） | 速度 | 97分動画への換算（1パス分） |
|---|---|---|---|
| 生エンコード fast、threads=既定（4） | 113秒 | 1.6倍速（48fps） | 61分 |
| 生エンコード veryfast、threads=既定（4） | 66秒 | 2.74倍速（82fps） | 35分 |
| edit.py フルパイプライン（2パス、preset fast） | 201秒 | 2パス合計で0.90倍速相当 | 108分 |
| edit.py フルパイプライン（2パス、preset veryfast） | 147秒 | 2パス合計で1.22倍速相当 | 79分 |

素材Bは素材A（testsrc2）の約3倍速くエンコードできた。画面の大半が静止している録画では、x264が静止部分をスキップするためである。実際のZoom録画は素材Bに近い構成（スライド＋小さな話者映像）のため、**素材Bの数値が現実の処理時間に近い**とみるべきである。ただし実際の録画は、画面共有の切り替え・ギャラリービュー・カメラ映像の動きなどで素材Bより重くなる場合があるため、実素材での再実測が必要である。

### 5.4 判定

**このVM（共有1.5CPU）では、重い素材の2パス構成は97分で約217分（edit.py実測。生エンコードを単純に2倍すると約350〜390分になるが、中間パスはカット後の短い本編のみを扱うため実測はこれより短い）かかり、15分以内には遠く及ばない。** スレッド数を1→2→4に増やしても速度が変わらない（0.559→0.538→0.534倍速）ことから、このVMでは共有CPUクォータが上限になっており、スレッド数ではなくCPUクォータがボトルネックであることが確認できた。したがって「コア数を増やせば速くなる」という見込みは、このVMの実測では裏付けられなかった。

**4コアの専用VPSへの外挿（あくまで目安）：** CPUクォータが1.5→4に増え、x264の処理量がCPU量にほぼ比例すると仮定すると、処理速度は約2.7倍になる。重い素材の1パスは約174分→約65分、2パス構成では約130分になる計算で、それでも15分以内には届かない。ただしこの外挿は「VPSの仮想コア1つあたりの性能がこのVMのEPYCコアと同等」という仮定に依存し、実際はホスト・CPUモデル・隣人テナントで変わる。**PoCで実機（KAGOYA 4GB）での再実測が必須**である。

**現行の本人のPC（約60分）との比較：** 本人のPCでは2パス構成で約60分かかっている。これは1パスあたり約30分、約3.2倍速に相当し、このVMの実測（約0.54倍速）の約6倍速い。PCのマルチコア性能が高いためとみられる。つまり「現行60分→15分以内」は、単に環境を変えるだけでは届かず、パイプライン側の高速化（§6）が必須である。

**Zoom風素材での判定：** 素材Bの実測結果（§5.3）をもとに、以下の見込みを立てる。

- このVM（共有1.5CPU）での1パスあたりの処理時間（97分換算）：fastで約61分、veryfastで約35分。2パス構成ではその約2倍（中間エンコードはcrf 15でさらに遅いため、実際はもう少しかかる。edit.pyの実測値で確認する）。
- **4コアの専用VPSへの外挿**（CPUクォータ1.5→4で約2.7倍速くなると仮定）：1パス・veryfastで約13分、2パス・veryfastで約29分（edit.py実測ベース）、1パス・fastで約23分、2パス・fastで約40分（edit.py実測ベース）。
- したがって、**15分以内を満たすには「4コアVPS＋1パス化＋veryfast」の3点セットが必須**で、2パス構成のままでは15分以内は満たせない見込みである。目標9分については、1パス・veryfastの外挿でも約13分かかるため、CPUエンコードだけでは届かない可能性が高く、GPUエンコード（§6.5）またはより高性能な環境の検討が必要になる。
- 無音検出は97分で約30秒と無視できる速さで、ボトルネックではない。ボトルネックは2回の映像エンコードである。

**edit.py フルパイプラインの実測値（2パス構成の実態）：** 180秒素材での実測は、testsrc2・preset fastで403秒、Zoom風・preset fastで201秒、Zoom風・preset veryfastで147秒だった。97分換算ではそれぞれ約217分・約108分・約79分になる。4コアVPSへの外挿（約2.7倍速と仮定）では、Zoom風・2パス・veryfastで約29分、Zoom風・2パス・fastで約40分になる。つまり**現行の2パス構成のままでは、4コアVPS＋veryfastでも15分以内には届かない**。1パス化（§6.1）でエンコード回数を半分にすれば、Zoom風・veryfastの外挿は約13〜15分になり、15分以内に入る見込みである。ただしこの外挿はCPU性能の仮定に依存するため、**PoCでの実機・実素材の実測が最終判定**になる。

なお、無音カットの中間エンコードはcrf 15（最終より高画質）で行われるため、中間パスは最終パスより遅い。1パス化は処理時間の半減だけでなく、この「遅い中間パス」をなくす効果もある。

**結論：** 処理時間の要件を満たすには、(a) 4コアのVPS、(b) 1パス化、(c) プリセット veryfast、の3点をセットで実施し、PoCで実機・実素材での処理時間を実測して確認する。実素材（Zoom録画）での実測が、最終的な合否判定になる。

## 6. パイプライン高速化案（処理時間が足りない場合）

現行パイプライン（`edit.py`）は、無音カット時に「中間エンコード（本編のみ、crf-3＝15、presetは設定値）＋本エンコード（OP/ED合成、crf 18）」の2パス構成である。処理時間の要件（15分以内・目標9分）を満たすために、以下の高速化案を優先度順に示す。

### 6.1 1パス化（最優先。処理時間をほぼ半減）

無音カットの中間ファイルをやめ、無音区間の切り出し（trim＋xfadeチェーン）を最終合成のフィルタグラフに直接組み込み、エンコードを1回にする。実装は `_build_main_cut` のフィルタ生成部分を最終合成の `[1:v]` / `[1:a]` 部分に統合する形になる。

- **効果**：エンコード回数が2回→1回になり、処理時間はほぼ半分になる。無音カットが不要な回（無音区間なし）では現行でも1パスなので、効果は無音カットがある回に限られる。
- **品質への影響**：ほぼなし。むしろ中間ファイルが高画質（crf 15）とはいえ一度劣化していた分がなくなるため、同等以上になる。
- **コストへの影響**：なし（同じVPS・同じLLM）。
- **注意点**：フィルタグラフが複雑化する。無音区間の数（97分で数十箇所程度と見込まれる）に対して、コマンドライン長・メモリ使用量を確認する必要がある。区間数が多い場合は、フィルタスクリプトファイル（`-filter_complex_script`）を使う。

### 6.2 プリセットの変更（medium→fast→veryfast）

現行の設定ファイル（`config.json`）は `preset: medium` になっている（コードの既定値は `fast`）。プリセットを `fast`、さらに `veryfast` に上げる。

- **効果**：§5の実測参照。medium→fastは約1.1倍とほぼ変わらない（360秒→337秒）。fast→veryfastは約1.7〜2.5倍（Zoom風：113秒→66秒、testsrc2：337秒→136秒）と大きく速くなる。プリセット変更の効果はほぼveryfastへの変更によるものである。
- **品質への影響**：小さい。同じcrfなら、プリセットは圧縮効率と速度のトレードオフで、画質の差は微小である。YouTube側で再エンコードされる前提でもあり、実質的な影響はほぼない。ファイルサイズは大きくなる（veryfastでmedium比＋20〜40%程度）が、YouTubeへのアップロードには問題ない。
- **コストへの影響**：なし。

### 6.3 crfの引き上げ（18→20〜23）

- **効果**：エンコード速度への影響は小さい（数%程度）。ファイルサイズは小さくなる。
- **品質への影響**：crf 20でもYouTube公開動画としては十分な画質だが、「現行の公開動画と同等」という品質基準との比較が必要。速度目的でcrfを上げる意義は薄いため、優先度は低い。

### 6.4 部分再エンコード（中期的検討。仕様変更とセット）

無音区間のカットだけをストリームコピー（再エンコードなし）でつなぎ、ディゾルブが必要な箇所だけ再エンコードする。

- **効果**：再エンコードする区間が全体の数%に減り、処理時間は数分レベルまで短縮できる可能性がある。
- **品質への影響**：大きい。現行仕様の「つなぎ目すべてにディゾルブ」を維持する限り、全編の再エンコードが必要である。部分再エンコードは、ディゾルブをやめる（カットのみにする）か、ディゾルブ区間だけを再エンコードする、という仕様変更とセットになる。品質基準（現行の公開動画と同等）との兼ね合いで、ユーザーと動画チームの合意が必要。
- **コストへの影響**：なし（実装コストのみ）。
- **注意点**：実装が複雑（concat demuxer＋再エンコード区間の挿入、タイムスタンプの整合）。PoC段階では採用しない。

### 6.5 GPUエンコード（NVENC等。将来の選択肢）

- **効果**：NVENC（h264_nvenc）は1080pでリアルタイムの数倍〜10倍のエンコードが可能で、15分以内・目標9分を楽に満たせる。
- **コストへの影響**：国内VPSのGPUは時間課金が中心。ConoHa GPUサーバー（NVIDIA L4）は60.5円/時、さくらインターネット「高火力 VRT」（NVIDIA V100）は481円/時。月4本×数分だけGPUインスタンスを起動する運用なら、月額は数百円に収まる計算になる。ただし常駐させると月36,300円〜と枠を大きく超える。
- **注意点**：ConoHaのGPUサーバーは2026-11-02時点で新規申込を制限中で、申請制（審査2〜3営業日）である。GPUインスタンスの起動・停止の自動化も別途必要。NVENCの画質は同ビットレートではlibx264よりやや劣る（crf相当の品質設定に注意）。第一案にはしないが、CPUでの処理時間がどうしても足りない場合の逃げ道として確保しておく。

### 6.6 その他（細かい高速化）

- **無音検出の高速化**：無音検出（`silencedetect`）は音声のみのデコードで、実測では数十倍速（§5参照）。ボトルネックではない。
- **解像度の見直し**：Zoom録画が720pの場合、1080pへのアップスケールをやめて720pのまま出すと、エンコード負荷が約半分になる。ただし現行の公開動画が1080pなら、品質基準との兼ね合いで要確認。
- **スレッド数の明示**：現行の `edit.py` はffmpegに `-threads` を渡しておらず、既定（論理CPU数）で動作する。VPSのコア数に合わせて明示的に指定し、メモリ使用量とのバランスを取る。

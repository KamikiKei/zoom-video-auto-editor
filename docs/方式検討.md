## Must要件（再掲）

- R1 定常作業が消える：録画取得〜非公開アップロードまで、人の定期作業がない
- R2 個人PCに依存しない
- R3 保守が特定個人に依存しない
- R4 月2,000円以内
- R5 品質が現行の公開動画と同等
- R6 公開は人が最終確認（自動アップロードは非公開）

## 候補H：エージェント方式（Claude等のAIエージェントが手順を実行）

2026-11-21 本人から追加。API連携を作らず、エージェントがブラウザ操作とスクリプト実行で工程を回す。

| 観点 | 評価 |
|---|---|
| R1 消える | △ 頼まれて実行する形では仕事が残る。スケジュール実行で自律化すれば消える |
| R2 PC非依存 | ○ 彼のPCは使わない |
| R3 保守・持続性 | ×〜△ 「彼のClaude」に載る限り属人化は形を変えて残る。ただし手順をプロンプト/スキルとして残せば別エージェントへ引き継ぎやすい（汎用性の高さが効く） |
| R4 コスト | △ 彼の利用枠内なら見かけの追加費用は小さい |
| R5 品質 | ○ 編集は現行スクリプトを使うため同等 |
| 汎用性 | ◎ 他イベント・他ツールにも同じやり方で対応できる。画面変更にも適応できる |
| 弱点 | UI操作はAPIより壊れやすい。97分動画のDL/編集/ULをエージェント基盤で処理する容量・速度に制約 |

位置づけ：**PoCと立ち上げの最速手段**。定常化の土台にするには R3 と処理基盤が課題で、「エージェントで回して検証 → 手順が固まったらスクリプト+APIに移す」段階移行が現実的。

## PoC結果（机上調査、2026-11-21）

1. **Zoom録画・VTTの自動取得：Proプランで可能**
   - 条件：クラウド録画ON＋「Create audio transcript」ON（現状VTTが取れているので満たしているはず）
   - 手段：Server-to-Server OAuthアプリ＋録画API。recording_files に TRANSCRIPT（VTT）と動画ファイルが download_url 付きで返る
   - 前提作業：アカウント管理者がS2S OAuthアプリを作成し録画スコープを付与すること（彼が管理者かどうかは要確認）
2. **YouTube APIアップロード：可能**
   - 2026-11-02 のポリシー変更で、未審査APIプロジェクトのアップロードが非公開に固定される制限が撤廃された（Google公式の改定履歴）
   - 既定クォータ（10,000ユニット/日）で月4本は問題なし
   - 注意：OAuth同意画面を「本番」状態にしないとリフレッシュトークンが7日で失効する
   - 本方式は「非公開で上げて人が公開に切り替える」決定と相性がよい
3. **安い環境での処理可否：未検証**（VPSスペックの実測が残る）

## 基本設計への申し送り（2026-11-21）

- 本人の見立て：工程には分岐・判断が多い（依頼と録画とconnpassの対応づけ、回ごとに変わるCanva素材の特定、判定の例外など）。このため「全部を固定スクリプトにする」よりエージェントが向く部分がある、という指摘
- 構成案：**エージェントが指揮、スクリプトが実行**。判断が要る工程（対応づけ、素材特定、例外の振り分け）はエージェント、定型で重い処理（編集そのもの）は現行スクリプト。人間は入口（依頼）と出口（公開確認）のみ
- 未決事項：定常運用で「誰のエージェント」が回すか（R3 保守・持続性に直結）。手順をプロンプト/スキルとして残し、コミュニティ側で運用する形が作れるかは基本設計で検討
- 実現性（2026-11-21 評価）：作っていける。重い定型処理（編集エンジン、VTT判定）は完成済みで、残りは接続部が中心。リスクは技術より権限系（Zoom管理者のS2Sアプリ作成、Slackアプリ承認、YouTubeチャンネルのOAuth）と、Canva取得の自動化の不安定さ。段階移行が可能：①エージェント指揮で1本通す（半自動PoC）→ ②頻出する分岐をスクリプト化 → ③定常化

## 結論

- **本決定（2026-11-21）：方式は G（自作開発）で進める。人間が残るのは判断が必要な工程（公開の最終確認・例外対応）のみとする**
- 要件を満たすのは **G のみ**（条件付き）。条件は PoC 3点：①Zoom APIで録画・VTTを取得できるか（机上調査では Pro で可能と確認）②YouTube APIで非公開アップロードできるか（同・可能と確認）③月2,000円以内の環境で97分動画を処理できるか（未検証）
- G の残存弱点は R3（保守の個人依存）。緩和策は基本設計で扱う：コードのチーム共用管理（GitHubは既にチーム外でも見られる形）、共用アカウント、手順書
- 前回メリデメで F・B が上位だったのは、「4人で回せればよい」が暗黙の前提だったため。本人の決定で目的が「分散」から「消去」に変わり、R1 が Must になった時点で順位がひっくり返った。要件定義が方式を決めた実例

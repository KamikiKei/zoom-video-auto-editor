# AI検出とデフォルト保持ポリシー

Zoom の文字起こし (VTT) をもとに、「最初からカット候補に入れておくべき区間」を
機械が提案し、人間がエディタのタイムラインでタップ切替して最終判断する仕組み。
判断が要る箇所は人間が担うが、判断は「候補への可否」で済むようにする
（要件定義の設計原則）ための実装。

候補はすべて plan の `silence.candidates` に乗り、各候補が
`source`（出所）と `kind`（種類）と `reason`（理由）を持つ。
エディタでは source ごとに帯の色が変わり、ブロックにマウスを乗せると
理由が表示される。候補をタップで無効化すると保持に戻る
（`disabled_cuts` として書き出しに渡る）。

## 候補の種類

| source | kind | 内容 | 出し方 |
|---|---|---|---|
| `silence` | silence | 一定秒数以上の無音 | ffmpeg silencedetect（従来） |
| `ops` | speaker | 運営（ホスト）らしい話者の発話 | ルールベース（下記ポリシー） |
| `other` | speaker | 登壇者でも運営でもない話者の発話 | ルールベース（下記ポリシー） |
| `llm` | trouble / fumbling / offtopic | トラブル対応・もたつき・本題外 | LLM 検出（下記） |
| `user` | user | 人間がタイムラインで直接切った区間 | エディタ操作 |

## デフォルト保持ポリシー（ルールベース・API不要）

- transcript があり、登壇者（plan の `presenters`）が決まっている場合、
  **登壇者以外の話者の発話区間を最初からカット候補にする**（デフォルト保持は登壇者のみ）。
- 運営らしい話者は source=`ops` に分ける。判定は次のどちらか:
  - 紹介文パターン（「ご紹介します」等）の直後に話した話者 = 登壇者なので、
    その紹介をした側 = 運営とみなす（transcript.py の登壇者推定と対）
  - 名前に 運営 / ホスト / 司会 / 主催 / 事務局 / スタッフ / コミュニティ /
    host / MC を含む（実アカウント名「松尾研 講義コミュニティ運営」に一致）
- それ以外の非登壇者は source=`other`。理由文には話者名が入る。
- 無効化: cfg `keep_presenters_only: false`、plan CLI は `--no-keep-presenters-only`。
  plan には `keep_policy: {keep_presenters_only, applied}` が記録される。
- 適用範囲は [開始点, 終了点] の内側のみ。開始点より前の導入部は従来どおり
  開始点カットで処理される。

## LLM 検出（llm_detect.py）

### API 選定: Google Gemini API（AI Studio）

- この工程は「候補を出して人間が最終判断する」もので、検出精度の差は
  最終品質に直結しない。したがって **無料枠で足りること** と
  **キー発行に課金登録（カード）が不要なこと** を決め手に Gemini を選んだ。
- エージェント基盤（Claude / Claude Agent SDK）とは独立した選定。
  パイプラインの判断役が Claude でも、検出役は別プロバイダでよい。
- 実装は `GeminiClient`（Python 標準ライブラリ urllib のみ、外部依存なし）。
  プロバイダ差し替え可能な抽象（`detect_window(cues)`）の上に載せてあり、
  代替として Anthropic Claude Messages API 向けクライアントも同じ抽象で
  実装可能（未実装）。
- モデル: 既定 `gemini-2.5-flash`、環境変数 `GEMINI_MODEL` で差し替え可能。
- JSON 出力の強制: Gemini の structured output
  （`responseMimeType: "application/json"` + `responseSchema`）を使う。
  応答スキーマは `{start_cue, end_cue, kind, reason, confidence}` の配列。

### 環境変数

| 変数 | 意味 |
|---|---|
| `GEMINI_API_KEY`（または `GOOGLE_API_KEY`） | Gemini API キー。無ければ LLM 検出はスキップ |
| `GEMINI_MODEL` | モデル ID（既定 `gemini-2.5-flash`） |
| `LLM_DETECT` | `mock` = モック検出を強制 / `off` = LLM 検出を無効化 |

### プロンプト設計

- 入力は番号付きキュー列（`[番号] 開始-終了秒 話者: テキスト`）。
  出力はキュー番号の範囲で指定させる（秒を直接言わせないことで、
  時刻のブレと範囲外参照を検証可能にする）。
- kind は3種に限定:
  - `trouble`: 音声・画面・接続などのトラブル対応
    （「聞こえますか」「画面が見えますか」「少々お待ちください」等）
  - `fumbling`: 言い淀み・フィラー連発・言い直しで実質的に進んでいない区間
  - `offtopic`: 本題と関係ない段取り確認・雑談
- **発表内容そのものと「考え中の間」は候補にしない** ことを明記している
  （間を詰めるのは無音カットの役目で、LLM 検出の対象ではない）。

### 呼び出し方法・出力検証

- 長い transcript は **約10分（600秒）の時間窓 + 60秒のオーバーラップ** に
  分割して順に呼ぶ。窓ごとに結果を受け、全体でマージする。
- 検証: kind のホワイトリスト、キュー番号の範囲内チェック、confidence の
  0–1 クランプ。不正な項目は捨てる。
- マージ: 同種で間隔1秒未満の候補は1つに連結（重なり窓で同じキューが
  二重に検出されても候補は1つになる）。

### 失敗時の挙動

- キーが無い / `LLM_DETECT=off` → 検出だけスキップ。plan に
  `llm_detection: {status: "skipped", ...}` を記録し、処理は続行する。
- API エラー・タイムアウト・不正な応答 → その窓は空として扱い、
  `status: "failed"`（detail に理由）を記録して plan は作る。
  **LLM の失敗で編集全体が止まることはない。**
- 書き出し側の保険: 1パス書き出しが失敗して従来方式（2パス）に
  フォールバックした場合も、保持区間（全方式のカットの結果）はそのまま
  適用される（回帰テスト Case L で担保）。

### コスト目安（97分1本あたり）

- 97分の文字起こしは概算 800〜1,000 キュー、日本語で約 45,000 トークン。
  窓のオーバーラップ込みで入力 約 50,000 トークン / 出力 約 3,000 トークン。
- Gemini 無料枠（Flash 系: 1日あたりのリクエスト数・トークン数の範囲内）で
  月4本程度なら十分に収まる見込み。**概算であり、枠の条件は変わりうる。**
- 有料枠に移った場合の概算: Flash 系の単価なら1本あたり数円〜十数円程度
  （概算。料金改定がありうるため断定しない）。

## エディタでの扱い

- タイムラインの帯: llm=紫、ops=濃紺、other=グレー、silence=従来色。
  凡例とブロックの title（種類 + 理由）で判別できる。
- 候補一覧の件数は出所別に表示される（例: AI検出2件・運営1件・無音3件）。
- エディタで有効にした llm 候補は `llm_cuts` として書き出しに渡り、
  plan にも候補として残る。ポリシー候補（ops/other）は書き出し時にも
  transcript から再計算され、無効化した分は `disabled_cuts` で保持に戻る。

## パイプライン連携

- デーモン（pipeline/daemon.py）は起動時に環境変数から LLM クライアントを
  決める（キーあり→Gemini / デモ→モック / それ以外→なし）。
- 確認依頼①の要約には候補の内訳（AI検出・運営・その他・無音・手動）と
  「AI検出に失敗した場合はその旨」が入る。
- デモ（pipeline/run_demo.sh）はモック検出で候補が付くところまで通る。

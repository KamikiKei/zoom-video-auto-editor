# 基本設計（ドラフト）— エージェント指揮 × スクリプト実行

前提：`現状分析.md` / `要件定義.md` / `方式検討.md`
設計原則：人間の関与は入口（依頼）と出口（公開確認）だけ。中間はエージェントとスクリプトで回す。

## 全体の流れと担当

| # | 工程 | 担当 | 内容 |
|---|---|---|---|
| 1 | 収録 | 仕組み（Zoom） | クラウド録画＋VTT生成 |
| 2 | 編集依頼 | **人間（入口）** | Slackで依頼。ここが唯一の起動点 |
| 3 | 対象の特定 | エージェント | 依頼文を読み、対象回の録画・connpassページ・Canva素材を対応づける |
| 4 | 録画＋VTT取得 | スクリプト（Zoom API） | エージェントの指示で対象分を取得 |
| 5 | OP/ED・サムネ取得 | エージェント | OP/EDは回ごとに変わるCanva素材（動画）から今回分を特定して書き出す。サムネはCanvaまたはGoogleスライド製で、同じく今回分を取得する（運用工夫で軽くできる可能性あり） |
| 6 | 登壇者・開始点の判定 | スクリプト（VTT解析） | 確信度が低い場合はエージェントが内容を見て判断、それでも怪しければ人間へ |
| 7 | 編集・書き出し | スクリプト（現行ツール） | カット / もたりカット / OP・ED接続 / ディゾルブ / エクスポート |
| 8 | 概要欄の生成 | エージェント | connpassのイベントページから取得して整形 |
| 9 | YouTubeアップロード | スクリプト（YouTube API） | 非公開でアップロード。タイトル・概要欄・サムネイルをセット |
| 10 | 完了通知 | スクリプト or エージェント | Slackに「確認お願いします」＋リンクを返す |
| 11 | 公開 | **人間（出口）** | 動画チームの誰かが最終確認して公開に切り替える |

## 次の検討事項：エージェント基盤の選定（基本設計の技術選定）

「どのAIか」はモデル単体の優劣ではなく、エージェント基盤として要件を満たすかで選ぶ。選定基準：

1. **ブラウザ操作ができるか**（Canva素材の取得に効く。最大の差別化点）
2. **コスト**：月4本＋例外対応の実行量で月2,000円以内に収まるか（判断はテキスト中心なので、1回あたりの消費は小さく見込む）
3. **共用アカウントで運用できるか**（APIキー方式など、個人に紐づかない形）
4. **日本語の読解・判断精度**（Slack依頼文、VTT、connpassの読み取り）
5. **外部連携のしやすさ**（Slack / Zoom / YouTubeとの接続手段）

並行する技術選定：実行環境（VPS等。PoC③と連動）。両方が詳細設計への入力になる。

## 担当の考え方

- エージェント：文脈を読む・対応づける・判断する工程（3, 5, 6の補助, 8）
- スクリプト：決定的で重い処理（4, 6の本処理, 7, 9）。現行ツールが土台
- 人間：入口と出口のみ。例外時はエージェントから判断を仰がれる

## ヒューマンインザループ（チェックポイント設計）

原則：チェック自体が定常作業にならないよう、「判断に必要な最小限」だけを見せて求める。確信度で分ける。

| チェックポイント | タイミング | 人間が見るもの | 進め方 |
|---|---|---|---|
| 対象特定の確認 | 依頼の直後 | エージェントの解釈（対象回・登壇者・素材） | 確信度が高ければ通知のみで進行。候補が割れたらSlackで確認を取ってから進む |
| カット案の確認・修正（任意） | 編集の前 | 開始点とカット区間（無音カット等）の一覧 | 残す/切るは判断の箇所なので、エージェントの案に対して人間が修正できるようにする。ただし必須確認にはしない（定常作業が戻るため）。修正がなければ案どおり進む（2026-11-21 本人指摘で追加） |
| 開始点の根拠提示 | 公開確認とセット | 開始点前後のVTT抜粋＋開始位置のタイムスタンプ | 最終チェック時に数秒で検証できる形で添える（動画を全部見せない） |
| 公開確認（出口） | アップロード後 | YouTubeリンク（非公開）、タイトル・概要欄、開始点、無音カット件数などの要約 | 動画チームの誰かが確認して公開。チェック所要は1分程度を設計目標にする |
| 例外のエスカレーション | 異常時 | 何が起きて、何に困っているか | 録画が見つからない / 素材が特定できない / VTTがない / 判定が割れる場合は、推測で進めず止まってSlackで聞く |

## 未確定・確認事項

- Slack依頼の形式：**チャンネルに来る**（確認済み）。文面に含まれる情報は未確認
- Canva素材：**動画（Canvaアニメーション）**（確認済み）。作り手は未確認。現行ツールの動画素材モードでそのまま扱える
- サムネイル：**CanvaとGoogleスライド**で制作（2026-11-21 本人確認）。取得はCanva API／Google Driveエクスポート（スライド→画像）の2経路。YouTube APIでサムネ設定まで自動化できる
- YouTubeタイトルの規則：**公開済み動画から判明**（本人確認済み）→ 通常回は `松尾研LLMコミュニティ【Paper&Hacks #<回数>】<発表タイトル>`。例：#103「VLM RAG 〜 目を持つRAG 〜」、#100「決定論的推論」。発表タイトルはconnpass側の記載とみられる
  - **例外：イベント回（特別回・他イベント）は形式が異なる**（本人指摘）。チャンネル上の実例にも「開発報告会 Vol.1」等の別形式がある。設計対応：エージェントがイベント種別を見て形式を選び、前例のない形式は人間に確認する（＝エージェント層が要る理由の具体例）
- 概要欄の中身：**公開済み動画（#103）から判明**（要本人確認）→ 定型ヘッダー（「本イベントは、原則毎週火曜日20:00から…」）＋ connpassのイベント概要ブロック（対象 / レベル / 発表者 / タイトル / 発表カテゴリ / イベント内容 / 扱う論文 / 注意・連絡事項）＋ 定型フッター（次回申込リンク、免責文、キーワード）。つまり概要欄は「固定部品＋connpass転記」で自動生成できる
- Zoomアカウントの管理者：**石川さん本人**（確認済み）→ Server-to-Server OAuthアプリを自分で作成できる。PoC①の前提はクリア
- 定常運用の主体：**運用専用の共用アカウントを1つ作り、チームで使って回す**（2026-11-21 本人決定）→ 運用主体を個人から切り離し、R3（保守・持続性）を満たす方向が決まった。サービスの権限は可能な範囲でロール付与（YouTubeチャンネルの管理者ロール等）にし、認証情報の共有は最小限にするのが基本設計の留意点
